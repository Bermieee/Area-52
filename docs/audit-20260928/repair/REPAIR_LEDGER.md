## Open decisions (not resolved by me)
- **O1** retirement policy with no revision oracle (above). Options: fix the test fixture to supply an oracle, or state in the contract that the fence is opt-in.
- **O2 (D14) `DEEP_BACKGROUND`**: docs evidence. `CAPABILITY_PROFILE_REGISTRY.md` lists `resourceClass` and `latencyClass` as profile fields but defines no value vocabulary; it says Runtime owns worker selection. `CONTINUOUS_CONSOLIDATION_WORKER.md` and `COGNITIVE_RUNTIME_FABRIC_WAVE2_ACCEPTANCE.md` describe DEEP as a Runtime scheduling lane (L3 Deep, borrow idle capacity via Resource Governor lease, yield/park/resume); the task also carries `resourceHints {borrowIdleCapacity, foregroundPreemptible}`. Nothing documents a profile being *typed* DEEP_BACKGROUND or the Connections UI setting it. Evidence leans scheduling class, but no document states it. Not changed. Owner must decide before D14 is fixed (likely: stop using `resourceClass` as a strict profile filter for DEEP, or add it to profile/Connections).
- **O4 (D7) authored Lore temporal/conflict semantics.** Evidence: the contract already carries `truthStatusHint`/`temporalHints` from Lore to Truth (WORKER4_LORE_COMPLETION_HANDOFF "Temporal semantics repair"); `owner-knowledge-channels.js` honours them (unknown -> UNRESOLVED). Root cause is upstream: the Lore Intelligence study engine (`lore-study-engine.js`) classifies every extracted claim CURRENT and does not read `metadata.at`/`claimAt`; `lore-study.js` (Core study) does model those fields but is not the installed Lore path; `store.conflicts()` reports `[]` for the golden lorebook. Fixing this means giving Lore's study engine temporal/conflict semantics (event ordering by `at`, claim-time by `claimAt`, conflict sets for same subject/predicate with different values). No document defines that for Lore Intelligence, so I did not invent it. Owner (Lore/Truth) decides: adopt `lore-study.js` temporal rules in the Lore study engine, or define new ones.
- **O5 (D11) native-path Jev.** JEV_WAVE11_NATIVE_OPTIONAL_ARCHITECTURE: the native path is native-first and Jev slots exist only when the host explicitly supplies configuration and an adapter. `CognitiveChoiceController.evaluateJev` already reports `JEV_UNAVAILABLE` (not SKIP) when >=2 unresolved alternatives exist and no adapter is registered, so the audit's "SKIP_JEV/JEV_NOT_REQUIRED" is a consequence of O4 (Truth produced no ambiguity), not a telemetry lie. Registering the deployment's Jev adapter on the native core is an owner decision.
- **O6 (D10 remainder) Runtime Batch Engine for Lore study.** BOARD_MAP #18/#30 say large work goes through the Runtime Batch Engine with yielding; the UI action still calls `brain.runLoreStudy` -> `runStudy({maxUnitsPerObligation: Infinity})` synchronously. Making it yield changes the operator adapter contract (`wave13-operator-adapters.js`, currently returns a synchronous receipt; wave13 UI tests are already failing on unrelated drift) and needs an owner-approved slicing/cancel design. Also unresolved: Diagnostics export size at large corpora (20.7 MB @ 1,200) and the ~1.3 s/turn of unattributed preparation cost. Sparse retrieval already reports `eligibleCount/indexedCount/boundedOutCount` (`production-sparse-retrieval.js`); whether the operator UI surfaces the 512-cap is a UI question.
- **O7 (D3) durable host store.** The extension exposes the seams (`persistNativeBrain`, `memoryOwnerSnapshot`, `loreOwnerSnapshot`, `nativeBrain`), but choosing the medium (SillyTavern chat metadata, IndexedDB, localStorage), its quota and privacy stance (snapshots contain narrative excerpts and Lore), when to restore, and how to reconcile a restored snapshot with the chat that is actually loaded is a product decision. I did not add a store. Scene owner persistence needs its own snapshot contract.
- **O3** host quiet/impersonate generations excluded from context (Wave 1 decision, unchanged).
